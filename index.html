1. Agent 基本原理

核心概念

  • Agent = 大模型 + 工具 + 循环 + 记忆。普通对话是"一问一答"，Agent 是让模型反复"思考 → 行动 → 观察"，直到任务完成。
  • Agent 循环（思考-行动-观察）：模型根据目标和当前信息思考下一步；决定调用某个工具（行动）；程序执行工具，把结果交回给模型（观察）；再进入下一轮，直到模型认为可以给出最终回答。
  • 模型只会生成文字。模型"调用工具"，其实是输出一段结构化文字（工具名 + JSON 参数）。真正执行永远发生在模型外面，由我们的代码完成。模型也没有记忆，每次请求都要把完整对话发过去。
模型负责：想和决定代码负责：记、做、管流程
理解用户意图
判断要不要用工具、用哪个
按 Schema 生成参数
根据工具结果组织最终回答		提供工具说明书（JSON Schema）
维护 messages（短期记忆）
解析参数、真正执行工具
把结果以 role: "tool" 回传
控制循环、步数上限、异常处理

LangChain、LangGraph 这些框架，本质上就是把右边这一列封装好了。

问：什么是 AI Agent？和普通的大模型调用有什么区别？
Agent 是以大模型为"大脑"、能自主调用工具完成多步任务的系统。普通调用是一次输入一次输出；Agent 会在一个循环里反复思考、调用工具、观察结果，直到完成目标。关键在于分工：模型只负责理解和决策，输出要调用的工具和参数；执行工具、保存记忆、控制流程都是程序在做。所以 Agent 的能力上限取决于模型的推理能力，而稳定性很大程度上取决于工程实现。
模型真的会"执行"工具吗？

不会。模型只生成"我要调用 X，参数是 Y"这段文字，程序解析后执行，再把结果作为新消息发回去。这也是为什么工具的安全边界要由代码来管。

Agent 和 Workflow（工作流）有什么区别？

Workflow 的步骤是代码预先写死的，可控、可预测；Agent 的下一步由模型动态决定，灵活但不稳定。实际项目常常混用：主干流程用工作流固定，局部需要灵活判断的地方交给 Agent。能用简单工作流解决的，不要硬上 Agent。

什么时候不该用 Agent？

任务步骤固定、对准确率和延迟要求很高、或者成本敏感时。Agent 多轮调用模型，慢、贵、而且结果有随机性。

小测验

2. Function Calling（工具调用）

核心概念

工具说明书：JSON Schema

{"type": "function",
 "function": {
   "name": "get_question",                       // 工具名，模型会原样输出它
   "description": "按主题从题库里取一道面试题",     // 模型靠它判断什么时候用
   "parameters": {                               // 参数格式，用 JSON Schema 描述
     "type": "object",
     "properties": {"topic": {"type": "string", "enum": ["工具调用", "规划", "记忆"]}},
     "required": ["topic"]                       // 必填字段
   }}}
  • name：工具名；description：写清"做什么、什么时候用"，这是模型选工具的主要依据；parameters：参数类型；enum：限定可选值；required：必填项。
  • 这段只是描述，不会执行任何东西。模型看不到你的 Python 函数，只看到这份说明书。

完整流程（背下来）

  1. 把 system 提示词 + 用户输入 + tools 说明书一起发给模型。
  2. 模型判断需要工具时，返回 tool_calls：每项有 id、function.name、function.arguments。注意 arguments 是 JSON 字符串，不是字典。模型也可能不调工具，直接回答。
  3. 先把这条 assistant 消息本身加入 messages（少了它，下一步的 tool 消息就"对不上号"，接口会报错）。
  4. json.loads(arguments) 解析参数，程序执行对应函数。
  5. 把结果以 {"role": "tool", "tool_call_id": call.id, "content": 结果} 加回 messages，tool_call_id 必须和调用的 id 一致。
  6. 再次请求模型，循环，直到返回里没有 tool_calls，此时的 content 就是最终回答。
  7. 用 for step in range(5) 之类的步数上限防止死循环。

动手看一遍：逐步展开 messages

返回的 msg 长什么样

ChatCompletionMessage(          # openai 库把返回的 JSON 包装成对象，所以能用 msg.content
    role="assistant",
    content="I'll fetch a planning-related interview question for you.",
    tool_calls=[ChatCompletionMessageToolCall(
        id="call_00_xxx", type="function",
        function=Function(name="get_question", arguments='{"topic": "规划"}'))])
# 调试：print(msg.model_dump()) 可以以字典形式打印
  • content 和 tool_calls 可以同时有值（DeepSeek 调工具前常顺口说一句），有的模型此时 content 是 None。代码不能假设二者只有一个。
  • messages 里可以混放普通字典和这个对象，SDK 发请求前会统一序列化成 JSON。
  • 同一份代码每次输出不同，是因为生成有随机性，主要由 temperature 控制；需要稳定输出时调低。

多工具：字典分发

TOOL_FUNCS = {"get_question": get_question, "record_score": record_score}
result = TOOL_FUNCS[name](**args)   # 按模型给的名字找函数；**args 把字典拆成关键字参数

加新工具只需在字典里加一行。几乎所有框架内部都是这么做的。实际项目里要处理"名字不存在"的情况（返回错误信息给模型，而不是让程序崩溃）。

什么该做成工具

  • 私有数据：公司题库、用户历史、内部文档，模型训练时没见过。
  • 实时信息：天气、股价、最新版本号，模型知识有截止日期。
  • 真实操作：写数据库、发邮件、调接口，模型只会生成文字。
  • 需要可控一致：要保证质量、去重、难度可控的内容。

判断标准：模型靠自己的知识能做好的，就让它直接答；需要外部数据或真实动作的，才做成工具。

问：讲一下 Function Calling 的原理。
Function Calling 是让模型以结构化格式表达"要调用哪个函数、传什么参数"的能力，是模型在训练阶段专门学过的。流程是：程序把 system、用户消息和用 JSON Schema 描述的工具列表一起发给模型；模型如果判断需要工具，就返回 tool_calls，里面有工具名和 JSON 字符串形式的参数；程序把这条 assistant 消息加入对话，解析参数并执行真实函数，把结果作为 role 为 tool 的消息、带上对应的 tool_call_id 回传；然后再请求模型，循环直到模型不再调用工具、给出最终回答。为防止死循环会设置最大步数。整个过程模型只负责决策，执行都在程序里。
模型输出的参数不合法（JSON 解析失败、缺字段、值越界）怎么办？

arguments 本质是模型生成的文本，可能出错。① 用 Pydantic / JSON Schema 校验；② 校验失败时把错误信息作为 tool 结果回传给模型，让它重试（设重试上限）；③ 用 strict 模式 / 结构化输出 / 约束解码（生成时只允许符合 Schema 的 token），从源头保证格式；④ 用 enum、明确的 description 降低出错率。

工具很多（几十上百个）时怎么办？

全部塞进请求会占大量上下文、增加成本，模型也更容易选错。做法：先检索工具（把工具描述向量化，按用户问题召回最相关的几个再交给模型），或按场景分组/路由，或拆给多个子 Agent，每个只管一组工具。

模型一次返回多个 tool_calls 怎么处理？

这叫并行工具调用。逐个（或并发）执行，每个结果都单独回传一条 tool 消息，各自带上对应的 tool_call_id。

工具执行报错了怎么办？

捕获异常，把错误信息作为工具结果返回给模型，让模型决定换参数重试或换方案；同时设置超时和重试上限，避免卡死。

为什么要把 assistant 那条带 tool_calls 的消息也加入 messages？

接口要求每条 tool 消息前面必须有对应的 assistant tool_calls 消息，模型才知道这个结果是回应哪次调用的。漏掉会报错。

3. 提示词与流程控制

核心概念

  • system 提示词设定角色、规则和流程，例如"一次只问一题；答完先调 record_score 打分再点评；低于 7 分针对遗漏追问，否则换题"。代码里没有写 if，模型自己按这段话决定调哪个工具。
  • 没写清楚的地方，模型就会自由发挥。例：只说"出一道题"，模型有时会"好心"附带参考答案；想固定行为就写明"只出题，不要给答案"。
  • 提示词控制：灵活但不可靠（模型偶尔不按流程走）；代码控制：可靠但不灵活。关键步骤（必须打分、必须鉴权、扣款）要用代码强制，例如用户回答后由代码直接调用评分，或用 LangGraph 固定节点顺序。
  • 好提示词的要素：角色、任务、步骤、约束（不要做什么）、输出格式、示例（few-shot）。

问：你怎么保证 Agent 按预期流程执行？
分两层。一层是提示词：在 system 里写清楚角色、步骤、约束和输出格式，必要时给示例，这能覆盖大部分情况。但提示词只是"建议"，模型有概率不遵守，所以对必须保证的关键步骤，我会把它放到代码里控制，比如用状态机或 LangGraph 固定节点顺序，用结构化输出加校验保证格式。原则是：灵活判断交给模型，硬性规则交给代码。
什么是 Context Engineering（上下文工程）？

比提示词工程更宽：不只是写好一句提示，而是设计每次请求里放什么——system 规则、检索到的资料、记忆、工具列表、历史摘要——以及放多少、怎么排序，让模型在有限的上下文里拿到最需要的信息。

怎么让模型输出稳定的 JSON？

用模型的 JSON mode / 结构化输出 / Function Calling；在提示词里给出格式示例；降低 temperature；程序端用 Pydantic 校验，失败则带着错误重试。

4. 规划与推理

核心概念

方法做法优点缺点
CoT 思维链让模型"一步一步想"，先写推理过程再给答案简单，提升推理题准确率只是思考，不和外界交互
ReActReason + Act 交替：想一步 → 调工具 → 看结果 → 再想灵活，能根据结果随时调整每步都调模型，慢、贵；长任务容易跑偏或绕圈
Plan-and-Execute先让模型列完整计划，再逐步执行（执行可用更小的模型），必要时重新规划全局清晰，步骤可控、省成本计划一开始错了不易发现，适应性弱于 ReAct
Reflection / Reflexion完成后让模型（或另一个模型）检查结果、指出问题再改；Reflexion 还把失败经验写成文字记忆用于下次尝试提升质量，能自我纠错多轮调用，成本和延迟增加

怎么选与结合：简单推理用 CoT；步骤不确定、要边查边做用 ReAct；任务长、步骤可预知用 Plan-and-Execute；对质量要求高再加 Reflection。常见组合：先规划，每个子步骤内部用 ReAct 执行，最后反思检查，失败则重新规划。我们写的那个"出题 → 评分 → 追问/换题"循环，就是一个简单的 ReAct。

问：ReAct 和 Plan-and-Execute 有什么区别？
ReAct 是推理和行动交替进行，每一步都根据上一步的观察结果决定下一步，适合步骤不确定、需要探索的任务，缺点是每步都要调用模型，长任务容易跑偏。Plan-and-Execute 先让模型制定完整计划，再按计划逐步执行，适合步骤较清晰的长任务，全局更可控、也能用小模型执行省成本，缺点是计划错了不容易纠正，所以通常会加"重新规划"环节。实际中常结合：先规划，子任务内部用 ReAct，最后再加反思校验。
Agent 陷入死循环 / 反复调用同一个工具怎么办？

设最大步数和超时；检测重复调用（同工具同参数）并提示模型换方法；把已尝试过的内容写进上下文；必要时转人工（Human-in-the-loop）。

推理模型（如 DeepSeek-R1）和 CoT 是什么关系？

推理模型通过强化学习训练，把"先长篇思考再回答"内化成了默认行为，相当于自带 CoT，不必再在提示词里要求"一步步想"。

5. 记忆

核心概念

  • 模型本身是无状态的，"记得"的前提是每次请求把需要的信息放进上下文。
  • 短期记忆：当前会话的 messages 列表。把它放在函数外面、每轮追加，就实现了多轮对话。问题是它越来越长：会超出上下文窗口、成本（按 token 计费）和延迟都上涨。处理方法：
    • 截断 / 滑动窗口：只保留 system + 最近 N 轮（注意别把 tool_calls 和对应 tool 消息拆开）；
    • 摘要：把早期对话让模型总结成一段文字放回去；
    • 工具结果太长时先截断或摘要再回传。
  • 长期记忆：跨会话保存的信息（用户偏好、"上次 RAG 答得不好"、历史分数），存在外部存储（关系库、KV、向量库）。需要时检索出来塞进提示词。写入时机可以是每轮结束后让模型抽取"值得记住的事实"。
  • 常见分类：语义记忆（事实，如用户是前端工程师）、情景记忆（过往经历/对话）、程序记忆（怎么做事的规则，常体现在提示词里）。

问：Agent 的短期记忆和长期记忆分别怎么实现？
短期记忆就是当前会话的消息列表，每次请求都完整发给模型。因为上下文窗口有限且按 token 计费，会用滑动窗口只保留最近几轮，或把早期内容总结成摘要。长期记忆是跨会话的，把用户偏好、关键事实、历史结果抽取出来存到数据库或向量库，下次对话时按相关性检索出来注入提示词。本质上长期记忆的读取就是一次 RAG。
记忆冲突或过期怎么办？

给记忆加时间戳和来源，新信息覆盖旧信息；定期合并、去重；重要事实可以让用户确认。

上下文窗口为什么有限制？越长越好吗？

注意力计算量随长度近似平方增长，KV Cache 显存也随长度线性增长；而且上下文越长，模型越容易忽略中间部分（lost in the middle）。所以不是越长越好，精挑细选的上下文效果更好也更便宜。

6. RAG（检索增强生成）

核心概念

RAG = 先查资料，再开卷作答。关键纠正：去资料里找的是程序，不是模型。程序把问题向量化、检索出相关片段，和问题一起放进提示词，模型只负责基于这些资料组织回答。

为什么需要：模型不知道私有资料和最新信息；资料太多不能全塞进上下文；答案有出处，能减少幻觉。

四步流程

  1. 切块：把文档切成小段。固定长度（如 500 字）+ 相邻块重叠，或按段落/标题切（语义切块）。太大检索不准，太小丢上下文。
  2. 向量化：把每块变成向量。和 fast.ai 里"像素变数字"是一个思想。
  3. 检索：问题用同一个模型向量化，和每块算相似度，取 top_k。
  4. 生成：把检索结果和问题拼进提示词，要求"只根据资料回答，没有就说不知道"。

TF-IDF vs 语义 Embedding

TF-IDF / BM25（稀疏向量）Embedding（稠密向量）
原理每一维是一个字/词，值看词频（TF）× 逆文档频率（IDF）：出现多、又只在少数块里出现，值就高神经网络训练出来的几百到上千维向量，意思相近的文字向量相近
擅长专有名词、型号、精确关键词换个说法也能找到（"编排工具"→ LangGraph）
短板只认字面，不懂语义精确术语、罕见词可能不准；需要模型
例子sklearn TfidfVectorizer、BM25（TF-IDF 改进版，考虑文档长度和词频饱和）中文常用 bge 系列、通义 text-embedding 等

余弦相似度 = 两个向量的点积 ÷ 两者长度之积，即夹角余弦，越接近 1 越相似。本质还是矩阵运算。

在线试一试：浏览器里跑的 TF-IDF 检索

向量数据库与 ANN

块有几百万个时不能逐个比较（暴力搜索），要用近似最近邻（ANN）：牺牲一点准确率换极快速度。最常见的算法是 HNSW（分层可导航小世界图：多层图结构，从稀疏的上层快速定位，再到稠密的下层精确查找），还有 IVF（先聚类、只搜最近的几个簇）等。常用库：Chroma、Milvus、Qdrant、Pinecone、PostgreSQL 的 pgvector（JD 里出现很多）、FAISS。

检索优化（面试高频）

  • 混合检索：BM25 关键词分数 + 向量语义分数，加权合并或用 RRF（倒数排名融合）合并两路结果。关键词保证专有名词准，语义保证换说法能查到。
  • Rerank 重排序：先粗召回 20~50 块，再用重排模型（cross-encoder，如 bge-reranker）把问题和每块一起输入，逐个判断相关度，取前 3~5。更准但更慢，只用在少量候选上。
  • 元数据过滤：先按条件（地区、日期、部门、权限）筛，再在范围内比相似度。
  • 查询改写：口语化/太短的问题先让模型改写、扩展同义词，或拆成多个子问题分别检索；多轮对话中要把"它呢？"补全成完整问题。
  • HyDE：先让模型凭空写一个"假答案"，再用假答案去检索。答案和资料的写法更像，往往比用问题搜更准。
  • 小块检索、大块返回（Parent Document / Small-to-Big）：用小块检索保证精准，返回时带上它所在的整段或父文档，保证上下文完整。

生成阶段

  • Lost in the middle：模型对放在长上下文中间的内容容易忽略，最相关的放开头或结尾，块数别太多。
  • 引用出处：给每块编号，要求模型标注 [1][2]，方便核对、减少编造。

评估

  • 检索：召回率（该找到的找到了没有）、精确率、MRR/命中率。需要准备"问题 → 应命中的块"的测试集。
  • 生成：忠实度（回答是否都有资料依据，不胡编）、答案相关性（是否答到了问题）。
  • 工具：RAGAS（faithfulness、answer relevancy、context precision/recall 等指标）；也常用 LLM 当裁判（LLM-as-a-judge）打分，再抽样人工复核。

进阶变体

  • Agentic RAG：把检索做成工具，让模型决定何时查、查什么、查几次、要不要改写关键词。我们的 rag.py 就是这种。传统 RAG 是每次固定先查一遍。
  • GraphRAG：先把资料抽取成知识图谱（实体 + 关系 + 社区摘要），适合需要综合多处信息的全局问题（"这些文档的主要主题是什么"）。代价是建图成本高。
  • RAG vs 长上下文：窗口变大后仍需要 RAG——资料量远超窗口、要控制成本和延迟、需要引用出处和权限控制时，RAG 更合适；资料少且固定时可以直接塞进上下文。
  • RAG vs 微调：知识常变、要出处 → RAG；要改变模型的风格、格式、特定任务能力 → 微调。两者可以结合。"知识用 RAG，行为用微调。"

文档解析

工具特点
Apache Tika支持一千多种格式（PDF/Word/Excel/PPT/邮件/HTML），统一接口提取文字和元数据，稳定、企业常用。缺点：只提文字不懂结构（表格被压平、标题层级和多栏排版丢失）；扫描件需额外配 Tesseract OCR；依赖 Java 服务（Python 的 tika 包会自动下载启动），部署多一个组件。
Unstructured把文档拆成标题、段落、表格等元素，方便按结构切块。

MinerU（国内团队开源）中文 PDF、公式、表格效果好。

问：什么是 RAG？为什么需要它？
RAG 是检索增强生成。离线阶段把文档解析、切块、向量化后存进向量数据库；在线阶段程序把用户问题用同一个模型向量化，检索出最相关的几段，和问题一起放进提示词，让模型基于资料作答。它解决了模型不知道私有和最新知识的问题，避免把大量资料全塞进上下文，并且答案可以引用出处，减少幻觉。
问：RAG 检索不准怎么优化？
先看数据：文档解析是否干净、切块大小和重叠是否合适，可以用小块检索大块返回。再看检索：上混合检索（BM25 + 向量），加 Rerank 精排，用元数据过滤缩小范围，对问题做查询改写或 HyDE。最后看生成：控制块数、把最相关的放在前面、要求引用出处。整个过程要用评估集量化：检索看召回率，生成看忠实度和相关性，可以用 RAGAS 或 LLM 裁判。
切块大小怎么定？

没有固定答案，取决于文档类型和问题粒度。常见起点 300~800 字（或 256~512 token）、重叠 10%~20%，再用评估集对比几组参数选最好的。结构清晰的文档优先按标题/段落切。

换了 Embedding 模型要做什么？

整个库都要重新向量化。不同模型的向量空间不兼容，维度也可能不同，问题和文档必须用同一个模型。

检索到的资料和问题无关，模型还硬答怎么办？

设相似度阈值，低于阈值视为没找到；提示词要求"资料不足就说不知道"；评估忠实度；必要时让 Agent 改写问题再查一次。

多轮对话里 RAG 怎么做？

先用模型结合历史把当前问题改写成独立完整的问题（如"那它的缺点呢？"→"HNSW 的缺点是什么？"），再去检索。

Rerank 为什么比向量检索准？

向量检索是问题和文档分别编码再比较（bi-encoder），信息交互少但快；Rerank 是把问题和文档拼在一起输入模型（cross-encoder），能细粒度判断相关性，但每对都要算一次，所以只用在少量候选上。

7. 多 Agent 协作

核心概念

  • 为什么要多个：单个 Agent 工具太多、提示词太长时容易混乱。按职责拆开，每个 Agent 只有自己的提示词和少量工具，更专注、更好调试。
  • 代价：调用次数多、成本和延迟高；Agent 之间传递信息会丢失上下文；出错难定位。能单 Agent 解决就不要多 Agent。
  • 框架：LangGraph（图里每个节点可以是一个 Agent）、CrewAI、AutoGen；Agent 之间的通信协议有 Google 提出的 A2A。

协作模式（图解）

① 主管-工人（Supervisor / Orchestrator）

主管理解目标、拆任务、选人分派，再汇总结果。优点：中心化控制，好追踪、好兜底。缺点：主管是瓶颈，所有信息都要过它，token 开销大。典型实现：LangGraph supervisor、"把子 Agent 当工具"。

② 顺序流水线（Sequential Pipeline）

像工厂流水线，顺序写死。优点：可预测、易调试、易评估每一环。缺点：不灵活，前面出错会一路传到下游。其实更接近"工作流"，很多场景这样就够了。

③ 辩论 / 评审（Debate / Review）

一个产出，一个批评（或两方辩论），裁判或规则决定是否通过。优点：质量更高，能抓出幻觉和漏洞（Reflection 的多 Agent 版）。缺点：成本成倍增加，可能争论不休，要设最大轮次和明确的通过标准。

④ 层级式（Hierarchical）

主管模式的"套娃"：上层只管下一层，每个组长本身又是一个小主管。优点：能拆超大任务，每层上下文都不大。缺点：层级越多延迟越高，信息逐层转述会失真。

⑤ 交接（Handoff）

当前 Agent 判断"这事该别人管"，把对话控制权整个交出去，之后由新 Agent 直接面对用户。常见于客服分流（OpenAI Agents SDK 的 handoff）。和主管模式的区别：交出去就不回来汇总。

通信方式：共享状态 vs 消息传递

共享状态（黑板模式）

所有 Agent 读写同一个状态对象（LangGraph 的 State、数据库）。优点：信息完整、谁都能看到全貌、方便持久化和断点恢复。缺点：要定义好字段结构；多个 Agent 同时写需要合并规则（LangGraph 用 reducer）；全部塞给每个 Agent 会让上下文膨胀。

消息传递

Agent 之间只传必要的信息（任务、结果、摘要）。优点：解耦、每个 Agent 上下文小、可以分布在不同服务甚至不同公司（A2A）。缺点：信息在转述中可能丢失，要设计好消息格式，全局状态难追踪。

问：什么时候用多 Agent？怎么设计？
当任务包含多个差异很大的子领域、单个 Agent 的工具和提示词过于庞杂时才拆。我常用主管-工人模式：主管负责理解目标、拆解和分派，子 Agent 各自持有专用工具和提示词，结果回到主管汇总。设计时要明确每个 Agent 的输入输出格式、共享状态放在哪里、以及最大轮次和失败兜底。同时要意识到多 Agent 成本和延迟更高，调试也更难，要配合可观测工具追踪每一步。
问：说说常见的多 Agent 协作模式。
主要有五种。主管-工人：中心主管分派和汇总，可控但主管是瓶颈。顺序流水线：步骤固定，上一个的输出给下一个，可预测但不灵活。辩论或评审：一个生成一个批评，质量高但成本翻倍，要限制轮次。层级式：主管套主管，适合超大任务，但层级多延迟高、信息会失真。交接：当前 Agent 把对话整个转给更合适的 Agent，常用于客服分流。选择时看任务是否可预先拆分、对质量和成本的要求。
多个 Agent 之间怎么共享信息？

两种：通过消息传递（把上一个的输出作为下一个的输入）；或共享状态（如 LangGraph 的 State 对象 / 数据库），各 Agent 读写其中的字段。共享状态信息完整、易持久化，但要处理并发写和上下文膨胀；消息传递解耦、上下文小，但信息可能在转述中丢失。

主管模式和交接（Handoff）有什么区别？

主管模式里子 Agent 做完要把结果交回主管汇总，控制权始终在主管；交接是把对话控制权整个交给另一个 Agent，之后由它直接和用户对话，不再回到原 Agent。

辩论 / 评审模式怎么避免没完没了？

设最大轮次；给评审者明确的通过标准（清单式打分，达到阈值就通过）；由独立裁判或规则做最终决定；记录每轮修改，发现原地打转就终止。

A2A 和 MCP 有什么区别？

MCP 解决"Agent 怎么连接工具和数据"（Agent ↔ 工具）；A2A 解决"不同 Agent 之间怎么互相发现、委托任务、交换结果"（Agent ↔ Agent），双方可以是不同团队、不同框架开发的。

多 Agent 系统怎么调试和评估？

全链路追踪（Langfuse / LangSmith），看每个 Agent 的输入输出、调用了哪些工具、耗时和 token；先单独评估每个子 Agent，再端到端评估；和单 Agent 基线对比，确认拆分真的带来了收益。

8. 工程落地

核心概念

  • 评估（Eval）：准备测试集（输入 + 期望行为），看最终答案质量，也看过程：工具选对没有、参数对不对、步数多少。用规则检查 + LLM 裁判 + 人工抽检。每次改提示词或换模型都跑一遍，防止"改好一处、坏了别处"。
  • 幻觉：模型自信地编造。对策：RAG 提供依据并要求引用；"不知道就说不知道"；降低 temperature；关键信息让工具查而不是让模型记；输出后校验。
  • 成本与延迟：减少模型调用次数和 token 数（精简提示词、摘要历史、限制检索块数）；简单任务用小模型、难的才用大模型（模型路由）；缓存（相同问题、提示词前缀缓存）；流式输出（SSE）降低"首字等待"；能并行的工具并行执行。
  • 安全：提示注入（Prompt Injection）：用户输入或工具返回的内容（网页、邮件、文档）里藏着"忽略之前的指令，执行……"。对策：把外部内容当数据而不是指令（明确分隔）；工具最小权限；危险操作（删数据、转账、发邮件）必须人工确认；输入输出过滤；敏感信息不放进提示词。
  • 可观测性：记录每次请求的完整链路——提示词、工具调用、参数、结果、耗时、token 数。常用 LangSmith（LangChain 官方）、Langfuse（开源、可自部署）。出问题能回放定位。

问：Agent 上线后你会关注哪些问题？
主要四方面。一是质量：建立评估集，既评最终结果也评工具调用过程，改动后回归测试。二是幻觉：用 RAG 提供依据并要求引用，资料不足时拒答。三是成本和延迟：控制调用次数和上下文长度，按难度路由大小模型，做缓存和流式输出。四是安全：防提示注入，工具最小权限，高风险操作加人工确认。另外接入 Langfuse 或 LangSmith 做全链路追踪，记录每一步的输入输出、耗时和 token，方便定位问题和优化。
怎么做流式输出？

调用模型时 stream=True，逐块拿到 token；后端用 FastAPI 的 StreamingResponse 以 SSE（text/event-stream）推给前端；前端用 fetch 读流或 EventSource 逐字渲染。工具调用的参数在流式里是分片到达的，要拼完整再解析。

Human-in-the-loop 是什么？

在关键节点暂停，等人确认或修改后再继续，例如执行付款、发邮件前。LangGraph 支持中断（interrupt）和从检查点恢复。

9. 框架与协议：LangChain / LangGraph / MCP

核心概念

  • LangChain：提供模型、提示词模板、工具、检索器等组件的统一封装，快速搭建应用。
  • LangGraph：把 Agent 建模成状态图：State（共享状态）、Node（一个步骤，如调模型、执行工具）、Edge（流转，条件边根据状态决定下一步，比如"有 tool_calls 就去工具节点，没有就结束"）。支持循环、检查点持久化（记忆、断点恢复）、人工中断、多 Agent。我们手写的 for 循环，就是一个"模型节点 ⇄ 工具节点"的两节点图。JD 里点名 LangGraph 的有 22/24 份。
  • 其他：LlamaIndex（偏 RAG 数据处理）、CrewAI、AutoGen（多 Agent）、Dify / Coze（低代码平台）。
  • MCP（Model Context Protocol）：Anthropic 2024 年提出的开放协议，统一"AI 应用如何连接外部工具和数据"。MCP Server 暴露工具（tools）、资源（resources）、提示模板（prompts）；MCP Client（在 Claude Desktop、Cursor 等宿主应用里）连接 Server，发现并调用它们。传输方式有 stdio（本地进程）和 HTTP（Streamable HTTP）。Python 可用官方 SDK 或 FastMCP 快速写 Server。
  • Function Calling 和 MCP 的关系：Function Calling 是模型的能力和 API 格式（模型怎么表达"调哪个工具"）；MCP 是工具的接入标准（工具怎么被发现、怎么被调用）。MCP 解决的是 M 个应用 × N 个工具要各写一遍集成的问题，写一次 Server，所有支持 MCP 的应用都能用。最终模型调用 MCP 工具时，底层仍然是 Function Calling。

问：为什么用 LangGraph？和自己写循环比有什么好处？
自己写循环能理解原理，但真实项目需要分支、循环、状态持久化、断点恢复、人工审批、多 Agent 协作和可视化调试，这些手写很容易乱。LangGraph 把流程建模成状态图，节点是步骤、边是流转规则，关键路径可以用代码固定，局部再交给模型决策，可控性比纯 ReAct 循环更好，还自带检查点做记忆和恢复。
问：MCP 是什么？解决什么问题？
MCP 是一个让 AI 应用以统一方式连接外部工具和数据的开放协议，采用客户端-服务器架构。工具提供方实现一次 MCP Server，暴露 tools、resources、prompts，任何支持 MCP 的客户端都能自动发现和调用，避免每个应用、每个工具都写一遍定制集成。它和 Function Calling 是互补的：MCP 管工具怎么接入，Function Calling 管模型怎么决定调用。
MCP 有什么安全风险？

第三方 Server 可能返回恶意内容（提示注入），或工具描述被篡改诱导模型；权限过大可能误删数据。要只用可信 Server、最小权限、敏感操作人工确认。

10. 大模型底层路线

核心概念

从 fast.ai 学过的 wx+b、矩阵、softmax 出发，到大模型还差这几步：

  1. Tokenization 与 Embedding：文字先切成 token（常用 BPE 等子词算法，一个汉字可能是 1 个或多个 token），每个 token 查表变成一个向量（embedding），再加上位置信息。和"像素变数字"是同一思路。
  2. Transformer 与注意力：每个 token 的向量分别乘三个矩阵得到 Q（查询）、K（键）、V（值）。Attention = softmax(Q·Kᵀ / √d) · V：Q 和所有 K 做点积算"该关注谁"，softmax 变成权重，再对 V 加权求和。生成时用因果遮罩，只能看前面的 token。多头注意力 = 并行做多组。再叠加前馈网络（就是 wx+b + 激活函数）、残差和归一化，堆几十层。
  3. 训练目标：预测下一个 token。最后一层输出整个词表上的分数，softmax 得到概率，损失函数是交叉熵，和数字分类一样，只是"类别"变成了整个词表（几万到十几万个）。
  4. 预训练 → SFT → RLHF：预训练在海量文本上学语言和知识（只会"续写"）；SFT 指令微调用"指令-回答"数据教它听指令、对话、按格式调用工具（所以模型"会" Function Calling）；RLHF（或 DPO 等）用人类偏好让回答更有用、更安全；推理模型还会用强化学习训练长思考。
  5. 推理参数：
    • temperature：除以温度后再 softmax，低→更确定，高→更随机多样；
    • top-p：只在累计概率达到 p 的最小候选集合里采样；
    • KV Cache：逐 token 生成时，缓存前面 token 的 K、V，不用每步重算，加速推理，但占显存；
    • 上下文窗口：一次能处理的最大 token 数（输入 + 输出），受注意力计算量（随长度平方增长）和显存限制。
推荐学习：Andrej Karpathy 的 Neural Networks: Zero to Hero，风格和 fast.ai 很像，从代码出发，最后用 PyTorch 从零手写一个小 GPT。建议主线做 Agent 项目，副线每周看一两集。

问：简单讲讲注意力机制。
注意力让每个 token 根据上下文动态决定关注哪些其他 token。具体是把每个 token 的向量投影成 Q、K、V 三个向量，用当前 token 的 Q 和所有 token 的 K 做点积，除以根号 d 防止数值过大，经过 softmax 得到注意力权重，再用权重对 V 加权求和，得到融合了上下文的新表示。多头注意力是并行做多组，让模型从不同角度关注信息。整个过程本质就是矩阵乘法加 softmax，可以高度并行。
为什么要除以 √d？

维度 d 大时点积数值会很大，softmax 会变得非常尖锐（接近 one-hot），梯度变小、训练不稳定。除以 √d 让数值保持在合适范围。

temperature 设为 0 就一定输出相同吗？

理论上接近贪心解码（每次选概率最高的），但由于 GPU 浮点计算、批处理等因素，实际服务中也不保证完全一致。

为什么模型会"幻觉"？

它的训练目标是生成"看起来最可能的下一个 token"，而不是"真实的事实"；遇到不知道的内容也会生成流畅但错误的文字。

11. 实战代码

三个脚本都用 OpenAI SDK 连 DeepSeek（base_url="https://api.deepseek.com"，模型 deepseek-chat），Key 从环境变量 DEEPSEEK_API_KEY 读取。不要把 Key 写进代码再上传 GitHub。源码也在仓库的 code/ 目录。

(a) 最小 Agent：get_question

一个工具、一次任务，模型一共被请求两次：第 1 次返回 tool_calls，第 2 次拿到题目后给出回答。

# 第一版：最小 Agent，只有一个 get_question 工具
# 运行前：在 PowerShell 里设置 $env:DEEPSEEK_API_KEY="你的key"（不要把 Key 写进代码）
import json, os
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],   # 方括号里是变量名，不是 Key 本身
                base_url="https://api.deepseek.com")

QUESTIONS = {
    "工具调用": "请解释 Function Calling 的原理。",
    "规划": "ReAct 和 Plan-and-Execute 有什么区别？",
    "记忆": "Agent 的短期记忆和长期记忆分别怎么实现？",
}

def get_question(topic: str) -> str:
    return QUESTIONS.get(topic, "题库里没有这个主题")

tools = [{
    "type": "function",
    "function": {
        "name": "get_question",
        "description": "按主题从题库里取一道 Agent 面试题",
        "parameters": {
            "type": "object",
            "properties": {"topic": {"type": "string", "enum": list(QUESTIONS)}},
            "required": ["topic"],
        },
    },
}]

def run_agent(user_input: str) -> str:
    messages = [
        {"role": "system", "content": "你是 Agent 面试官，需要时用工具取题。"},
        {"role": "user", "content": user_input},
    ]
    for step in range(5):                      # 步数上限，防止死循环
        resp = client.chat.completions.create(
            model="deepseek-chat", messages=messages, tools=tools)
        msg = resp.choices[0].message
        messages.append(msg)                   # 先把 assistant 消息本身加进去
        if not msg.tool_calls:                 # 没有工具调用 = 最终回答
            return msg.content
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)   # arguments 是 JSON 字符串
            print(f"[第{step + 1}步] 调用 {call.function.name}({args})")
            result = get_question(**args)
            messages.append({"role": "tool",
                             "tool_call_id": call.id, "content": result})
    return "超过最大步数"

if __name__ == "__main__":
    print(run_agent("给我出一道关于规划的面试题"))

(b) 面试官：多工具 + 多轮对话

新东西：① record_score 工具（模型能打分但存不下来）；② TOOL_FUNCS 字典分发；③ 详细 system 提示词约束流程（低于 7 分追问，否则换题）；④ messages 移到函数外，跨轮累积 = 短期记忆。需要在自己的 PowerShell 里运行，因为要键盘作答。

# 第二版：多工具 + 多轮对话的面试官（get_question + record_score）
import json, os
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                base_url="https://api.deepseek.com")

QUESTIONS = {
    "工具调用": "请解释 Function Calling 的原理。",
    "规划": "ReAct 和 Plan-and-Execute 有什么区别？",
    "记忆": "Agent 的短期记忆和长期记忆分别怎么实现？",
}
scores = []  # 记录每次评分，相当于一个简单的"数据库"

def get_question(topic: str) -> str:
    return QUESTIONS.get(topic, "题库里没有这个主题")

def record_score(topic: str, score: int, missing: str) -> str:
    scores.append({"topic": topic, "score": score, "missing": missing})
    avg = sum(s["score"] for s in scores) / len(scores)
    return f"已记录。目前共答 {len(scores)} 题，平均分 {avg:.1f}"

TOOL_FUNCS = {"get_question": get_question, "record_score": record_score}

tools = [
    {"type": "function", "function": {
        "name": "get_question",
        "description": "按主题从题库取一道面试题。开始面试或换题时使用。",
        "parameters": {"type": "object",
            "properties": {"topic": {"type": "string", "enum": list(QUESTIONS)}},
            "required": ["topic"]}}},
    {"type": "function", "function": {
        "name": "record_score",
        "description": "候选人回答问题后，给回答打分（1-10）并记录遗漏的要点。",
        "parameters": {"type": "object",
            "properties": {
                "topic": {"type": "string", "enum": list(QUESTIONS)},
                "score": {"type": "integer", "minimum": 1, "maximum": 10},
                "missing": {"type": "string", "description": "回答中遗漏的关键点"}},
            "required": ["topic", "score", "missing"]}}},
]

SYSTEM = """你是严格但友好的 AI Agent 面试官。流程：
1. 用 get_question 取题并提问，一次只问一题。
2. 候选人回答后，先调用 record_score 打分，再简要点评。
3. 分数低于 7 分就针对遗漏点追问一次；否则换一个新主题。"""

messages = [{"role": "system", "content": SYSTEM}]   # 放在函数外 = 跨轮次的短期记忆

def agent_turn(user_input: str) -> str:
    messages.append({"role": "user", "content": user_input})
    for step in range(5):
        resp = client.chat.completions.create(
            model="deepseek-chat", messages=messages, tools=tools)
        msg = resp.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:
            return msg.content
        for call in msg.tool_calls:
            name = call.function.name
            args = json.loads(call.function.arguments)
            print(f"  [工具] {name}({args})")
            result = TOOL_FUNCS[name](**args)   # 按名字分发到对应函数
            messages.append({"role": "tool",
                             "tool_call_id": call.id, "content": result})
    return "超过最大步数"

print("面试官：", agent_turn("我准备好了，开始面试吧"))
while True:
    answer = input("\n你：")
    if answer in ("q", "退出"):
        break
    print("\n面试官：", agent_turn(answer))

(c) rag.py：TF-IDF 版 Agentic RAG

资料是同目录的 agent_jd_summary.md。按行切块（>10 字），TfidfVectorizer(analyzer="char", ngram_range=(1, 2)) 按单字和双字建向量（中文不需要分词库），余弦相似度取 top 5，包装成 search_jd 工具。argsort() 从小到大排下标，[::-1] 反转，[:top_k] 取前几个。

# 第三版：最小 RAG（TF-IDF 版），把 JD 资料做成 search_jd 工具交给 Agent
# 依赖：python -m pip install openai scikit-learn
import json, os
from openai import OpenAI
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                base_url="https://api.deepseek.com")

# ---------- 第 1 步：切块 ----------
with open("agent_jd_summary.md", encoding="utf-8") as f:
    text = f.read()
chunks = [c.strip() for c in text.split("\n") if len(c.strip()) > 10]
print(f"资料切成了 {len(chunks)} 块")

# ---------- 第 2 步：向量化 ----------
# 按单字和双字切词，中文不需要额外分词库
vectorizer = TfidfVectorizer(analyzer="char", ngram_range=(1, 2))
chunk_vectors = vectorizer.fit_transform(chunks)

# ---------- 第 3 步：检索 ----------
def search_jd(query: str, top_k: int = 5) -> str:
    query_vector = vectorizer.transform([query])
    scores = cosine_similarity(query_vector, chunk_vectors)[0]
    best = scores.argsort()[::-1][:top_k]          # 相似度最高的 k 块
    return "\n".join(chunks[i] for i in best)

# ---------- 第 4 步：把检索做成工具，交给 Agent ----------
tools = [{"type": "function", "function": {
    "name": "search_jd",
    "description": "从收集的 AI Agent 岗位 JD 资料中检索相关内容。"
                   "回答关于招聘要求、技能、岗位的问题时必须使用。",
    "parameters": {"type": "object",
        "properties": {"query": {"type": "string",
                                 "description": "检索关键词或问题"}},
        "required": ["query"]}}}]

messages = [{"role": "system", "content":
    "你是求职顾问。回答前先用 search_jd 检索资料，只根据检索结果回答，"
    "资料里没有的就说不知道，不要编造。"}]

def agent_turn(user_input: str) -> str:
    messages.append({"role": "user", "content": user_input})
    for step in range(5):
        resp = client.chat.completions.create(
            model="deepseek-chat", messages=messages, tools=tools)
        msg = resp.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:
            return msg.content
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)
            result = search_jd(**args)
            print(f"  [检索] {args['query']}\n  [命中]\n{result}\n")
            messages.append({"role": "tool",
                             "tool_call_id": call.id, "content": result})
    return "超过最大步数"

while True:
    q = input("\n你：")
    if q in ("q", "退出"):
        break
    print("\n顾问：", agent_turn(q))

TF-IDF 版和真正的 RAG 差在哪？

流程完全一样，差别只在向量化：TF-IDF 只比字面重合，本质更像关键词检索；换成 embedding 模型（如 bge）就是语义检索，再把 numpy 计算换成向量数据库即可。

os.environ["DEEPSEEK_API_KEY"] 方括号里该写什么？

环境变量的名字，程序会用它去查对应的值。把 Key 本身写进去会报 KeyError，还会让 Key 出现在报错信息里。

$env:X="..." 和 setx X "..." 有什么区别？

$env: 只对当前 PowerShell 窗口（进程）有效，关掉就没了；setx 写入用户环境变量，永久有效，但要重新打开窗口才能读到。

pip 报 from versions: none 怎么排查？

说明 pip 没连上软件源。换国内镜像并加 --trusted-host；加 -v 看卡在哪；检查 VPN / 代理设置；确认 Python 版本不太老。

为什么要用虚拟环境？怎么建？

每个项目依赖独立，互不影响，也不会污染别的软件自带的 Python。python -m venv .venv 建，.\.venv\Scripts\Activate.ps1 激活，提示禁止运行脚本就先 Set-ExecutionPolicy -Scope CurrentUser RemoteSigned。

装了 scikit-learn 还是 No module named 'sklearn'？

包名 scikit-learn、导入名 sklearn，名字不同是正常的。仍报错多半是 pip 和 python 不是同一个解释器，用 python -m pip install 装。
